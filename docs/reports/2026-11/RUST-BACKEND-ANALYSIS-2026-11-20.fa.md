# بردن بک‌اند Xomoni به Rust: مزیت‌ها، تهدیدها و فرصت‌ها

> - **تاریخ:** ۲۰ نوامبر ۲۰۲۶.
> - **سؤال نگه‌دارنده:** آیا بک‌اند Xomoni را به زبان Rust تغییر دهیم؟
> - **منابع:** هر ادعای بیرونی لینک منبعش را در [بخش منابع](#منابع) دارد. چیزی که نتوانستم تأیید کنم با «تأییدنشده» آمده است.
> - **عددهای خود Xomoni:** از کد همین مخزن در همین تاریخ شمرده شده‌اند.

## جواب کوتاه

- **الان نه.** بازنویسی بک‌اند به Rust، در وضع امروز Xomoni، هزینه‌ی زیادی دارد و برای کاربر تقریباً هیچ سود قابل اندازه‌گیری‌ای ندارد.
- **دلیل اصلی:** Xomoni تقریباً بک‌اند اختصاصی ندارد.
  - کد سمت سرور ما حدود ۶۵۰ خط SQL و حدود ۷۰۰ خط TypeScript است. بقیه سرویس‌های آماده‌ی Supabase است.
  - کار سنگین عمداً در مرورگر کاربر انجام می‌شود، چون داده‌ی X نباید از مرورگر بیرون برود.
- **هزینه‌ی بازنویسی:** چند هفته توقف داشبورد، که الان اولویت اول شماست. ریسک خطاهای تازه هم دارد.
- **Rust یک جای درست دارد:** وقتی Xomoni کار زمان‌بندی‌شده یا دائمی روی سرور پیدا کند. اولینش ایمیل هفتگی است، یعنی کار ۱۸ از [۲۰ کار بعدی](NEXT-20-TASKS-2026-11-20.fa.md). آنجا یک سرویس کوچک و جدای Rust کم‌خطر و قابل برگشت است.
- **پیشنهاد من:**
  - Next.js، Supabase و TypeScript بمانند.
  - اگر می‌خواهید Rust را از نزدیک امتحان کنید، کار ۱۸ را به‌عنوان آزمایش محدود (حداکثر یک هفته، با معیار موفقیت روشن) با Rust بسازیم.
  - تصمیم نهایی با یک ADR ثبت شود.

## ۱. بک‌اند Xomoni امروز دقیقاً چیست؟

| بخش | زبان | اندازه | کجا اجرا می‌شود | چه کاری می‌کند |
| --- | --- | --- | --- | --- |
| Postgres در Supabase | SQL | ۱۲ migration، حدود ۶۵۰ خط، ۵ جدول، ۱۳ تابع، Row Level Security روی همه، ۸ فایل تست pgTAP | Supabase | حساب‌ها، مرورگرهای وصل‌شده، وضعیت کارها، کد اتصال یک‌باره |
| Auth، Realtime و ایمیل | سرویس آماده | کد ما نیست؛ فقط تنظیمات در `supabase/config.toml` | Supabase و Resend | ثبت‌نام، ورود با رمز و گوگل، Turnstile، بازیابی رمز، پیام زنده |
| سرور سایت | TypeScript | حدود ۷۰۰ خط | Vercel، داخل Next.js 16 | فرم‌های ورود، نشست، proxy و بارگذاری داشبورد |
| موتور افزونه | TypeScript | حدود ۸٬۵۰۰ خط: engine ۲٬۸۰۰، shared ۳٬۶۰۰، content ۱٬۱۰۰ و cloud ۷۰۰، به‌علاوه‌ی ۹٬۷۰۰ خط رابط کاربری | مرورگر کاربر | کار اصلی Xomoni: اسکن، پاک‌سازی، کنترل سرعت و آرشیو |
| قراردادهای مشترک | TypeScript | `packages/bridge` و `packages/db` | هر دو طرف | یک تعریف برای سایت و افزونه، که نمی‌گذارد دو طرف از هم جدا شوند |

**سه واقعیت تصمیم را تعیین می‌کنند:**

1. **بخش بزرگ بک‌اند SQL است و در هر حالت SQL می‌ماند.** Rust جای Postgres، Row Level Security یا تست‌های pgTAP را نمی‌گیرد.
2. **کار سنگین در مرورگر است، به حکم [ADR-0004](../../adr/0004-x-data-stays-local.md):** متن پست‌ها و لایک‌ها از مرورگر بیرون نمی‌روند. Rust روی سرور اصلاً به این بخش نمی‌رسد.
3. **سرعت Xomoni عمداً پایین است.** Xomoni هرگز بیش از یک‌پنجم سقف X کار نمی‌کند ([ADR-0012](../../adr/0012-one-fifth-of-every-x-limit.md)). گلوگاه پردازنده نیست، قانون ایمنی است. سریع‌تر شدن کد کار کاربر را سریع‌تر نمی‌کند.

## ۲. «بک‌اند را Rust کنیم» چهار معنی می‌تواند داشته باشد

### راه الف: سرور سایت در Rust، سایت همچنان Next.js

- **چه می‌شود:**
  - آن ۷۰۰ خط به یک API جدا در Rust منتقل می‌شود (مثلاً با Axum).
  - این API نشست Supabase را با کلید عمومی‌اش (JWKS) تأیید می‌کند.
  - روی Vercel (اجرای Rust در Vercel هنوز بتا است) یا روی یک میزبان جدید اجرا می‌شود.
- **برآورد من:** ۲ تا ۳ هفته، با تست‌ها و CI.
- **سود برای کاربر:** تقریباً صفر. هر درخواست یک مرحله‌ی شبکه‌ی اضافه هم پیدا می‌کند.

### راه ب: کنار گذاشتن Supabase و ساختن Auth و Realtime در Rust

- **چه می‌شود:** ثبت‌نام، ورود، گوگل، Turnstile، ایمیل‌ها، نشست‌ها و پیام زنده را خودمان می‌سازیم.
- **برآورد من:** ۲ تا ۳ ماه.
- **ریسک:** خیلی زیاد. Auth حساس‌ترین کد هر محصول است، و امروز Supabase آن را با تست‌های خودش نگه می‌دارد.
- **سود برای کاربر:** منفی.

### راه ج: همه‌چیز بماند، فقط کارهای تازه‌ی سرور با Rust

- **چه می‌شود:** فقط کارهای جدیدی که روی سرور اجرا می‌شوند با Rust ساخته می‌شوند:
  - ایمیل هفتگی؛
  - جمع‌بندی شبانه‌ی عددها؛
  - کارهای زمان‌بندی‌شده.
- **برآورد من:** حدود یک هفته برای اولین سرویس، به‌علاوه‌ی نگهداری.
- **ریسک:** کم، و قابل برگشت.
- **سود:** متوسط، به شرطی که کار سرور واقعاً زیاد شود.

### راه د: Rust به‌صورت WebAssembly داخل افزونه

- **چه می‌شود:** پارسرها یا باز کردن آرشیو X با Rust نوشته و به WebAssembly تبدیل می‌شوند.
- **برآورد من:** ۲ تا ۴ هفته.
- **سود:** تقریباً هیچ.
  - آرشیو همین الان با `DecompressionStream` خود مرورگر باز می‌شود، که کد بومی مرورگر است. `JSON.parse` هم بومی است.
  - رفت‌وبرگشت داده بین JavaScript و WebAssembly هزینه دارد. تیم OpenUI یک پارسر Rust/Wasm را با TypeScript عوض کرد و نسخه‌ی TypeScript ۲.۲ تا ۴.۶ برابر سریع‌تر بود.
  - در Chrome، `DecompressionStream` تقریباً هم‌سرعت سریع‌ترین کتابخانه‌ی JavaScript است.

## ۴. تهدیدها

1. **توقف کار اصلی.**
   - راه الف یا ب یعنی هفته‌ها بدون پیشرفت قابل دیدن روی داشبورد، یعنی دقیقاً همان چیزی که الان می‌خواهید.
   - هر انتقال خطای تازه می‌آورد. GitHub در انتقال runtime خود Copilot از TypeScript به Rust «ده‌ها» خطای تازه پیدا کرد؛ مثلاً عدد صحیح به شکل `42.0` نوشته می‌شد و رفتار `||` در JavaScript روی رشته‌ی خالی از دست رفت.
2. **دو زبان و دو قرارداد.**
   - امروز سایت و افزونه از یک تعریف مشترک استفاده می‌کنند: `@xomoni/bridge` و `@xomoni/db`.
   - با Rust این تعریف‌ها باید با ابزاری مثل ts-rs یا typeshare تولید شوند. یک مرحله‌ی اضافه و یک خطر ناهمخوانی اضافه می‌شود.
   - Prisma دقیقاً برعکس عمل کرد و موتورش را از Rust به TypeScript برد. دلیل‌ها:
     - هزینه‌ی تبدیل داده بین JavaScript و Rust؛
     - فایل جدا برای هر سیستم‌عامل؛
     - کم بودن همکارانی که هر دو زبان را بلدند.

     نتیجه: حجم بسته از ۱۴ به ۱.۶ مگابایت رسید و پرس‌وجوها تا ۳.۴ برابر سریع‌تر شدند.
3. **میزبانی و ابزار هنوز کامل نیست.**
   - اجرای Rust در Vercel از دسامبر ۲۰۲۵ بتا است و اعلام نسخه‌ی پایدارش را پیدا نکردم.
   - Supabase کیت رسمی Rust ندارد. کتابخانه‌های جامعه زیر نسخه‌ی ۱ هستند.
   - توابع Edge در Supabase فقط TypeScript روی Deno را اجرا می‌کنند. Rust آنجا فقط به شکل WebAssembly ممکن است.
   - Shuttle، میزبان مخصوص Rust، در ژانویه‌ی ۲۰۲۶ تعطیل شد و کاربرانش مجبور به جابه‌جایی شدند.
   - هر میزبان جدید یعنی حساب جدید، کلیدهای محرمانه‌ی جدید، پایش جدید، صورت‌حساب جدید و سطح حمله‌ی جدید.
4. **Auth.** ساختن Auth خودمان (راه ب) پرخطرترین کار ممکن است. در هر راه معقول، Auth در Supabase می‌ماند و Rust فقط نشست را تأیید می‌کند. این کار شدنی است: Supabase کلیدهای نامتقارن (ES256) و آدرس JWKS دارد، و کتابخانه‌ی `jsonwebtoken` نسخه‌ی ۱۲ از آن پشتیبانی می‌کند.
5. **همکاران کمتر برای یک پروژه‌ی متن‌باز.** در نظرسنجی Stack Overflow 2025، ۱۴.۸٪ برنامه‌نویس‌ها از Rust استفاده می‌کردند و ۴۳.۶٪ از TypeScript. یعنی کسانی که می‌توانند در Xomoni مشارکت کنند، کمتر می‌شوند.
6. **زمان کامپایل و CI طولانی‌تر.** در نظرسنجی کارایی کامپایلر Rust (۲۰۲۵):
   - میانگین رضایت ۶ از ۱۰ بود؛
   - ۵۵٪ برای ساخت دوباره‌ی بدترین پروژه‌شان بیش از ۱۰ ثانیه صبر می‌کنند؛
   - حدود ۴۵٪ کسانی که Rust را کنار گذاشتند، زمان کامپایل را دلیلش گفتند.

   `npm run verify` ما همین الان هم کند است.
7. **قانون‌های کیفیت پروژه باید از نو ساخته شوند.** هر کدام یک ADR و کار جدا می‌خواهد:

   | قانون امروز در TypeScript | معادلش در Rust |
   | --- | --- |
   | TSDoc روی هر export | rustdoc، با `#![deny(missing_docs)]` |
   | قانون‌های لایه با dependency-cruiser | مرزهای workspace در cargo |
   | `tests:check` و پوشش تست | cargo-llvm-cov |
   | lint سخت‌گیر | clippy |
   | زنجیره‌ی تأمین | cargo-deny و cargo-audit |

## ۵. فرصت‌ها

1. **کارهای سرور در آینده.**
   - ایمیل هفتگی (کار ۱۸) و جمع‌بندی شبانه‌ی عددها.
   - اگر روزی «حالت ابری با API رسمی X» برگردد (فعلاً کنار گذاشته شده)، یک worker دائمی با صف و کنترل سرعت جای طبیعی Rust است: پایدار، کم‌مصرف و قابل پیش‌بینی.
2. **Xomoni خود-میزبان.** یک فایل اجرایی کوچک که کاربران حساس به حریم خصوصی روی سرور خودشان اجرا کنند. برای یک پروژه‌ی متن‌باز جذاب است و Rust برایش بهترین گزینه است.
3. **هزینه‌ی ثابت پایین در مقیاس بالا.** اگر هزاران کاربر عدد روزانه بفرستند، کد Rust ارزان‌تر اجرا می‌شود. هرچند تا آن روز گلوگاه Postgres است، نه کد.
4. **تصویر فنی.** Rust در نظرسنجی Stack Overflow محبوب‌ترین زبان بود: ۷۲٪ در ۲۰۲۵ و ۶۷.۴٪ در ۲۰۲۶. «ساخته‌شده با Rust» علاقه‌مندان را جذب می‌کند. اثرش کوچک ولی واقعی است.
5. **یادگیری.** تجربه‌ی Rust برای شما در پروژه‌های بعدی ارزش دارد. یک آزمایش محدود این را بدون به خطر انداختن محصول می‌دهد.

## ۷. پیشنهاد من

1. **۲۰ کار بعدی با Next.js، Supabase و TypeScript جلو برود.** داشبورد کامل اولویت است.
2. **Rust فقط وقتی وارد شود که یکی از این نشانه‌های قابل اندازه‌گیری دیده شود:**
   - Xomoni کار دائمی یا زمان‌بندی‌شده‌ی سنگین روی سرور پیدا کند، مثلاً صف کار یا بیش از چند دقیقه پردازش در روز؛
   - هزینه‌ی Vercel یا Supabase به خاطر محاسبه، نه پایگاه داده، از سقفی که با هم تعیین کنیم بالاتر برود؛
   - تصمیم به نسخه‌ی خود-میزبان گرفته شود؛
   - اندازه‌گیری یک گلوگاه واقعی در افزونه نشان دهد WebAssembly آن را دست‌کم دو برابر سریع‌تر می‌کند.
3. **اگر با این حال می‌خواهید Rust را از نزدیک امتحان کنید،** کار ۱۸ (ایمیل هفتگی) را به‌عنوان آزمایش محدود با Rust بسازیم:
   - یک سرویس کوچک و جدا (راه ج)، روی اجرای Rust در Vercel یا Google Cloud Run که سهم رایگان ماهانه دارد؛
   - حداکثر یک هفته؛
   - **معیار موفقیت:**
     - همان سطح تست و قانون‌های کیفیت (rustdoc، clippy و cargo-deny)؛
     - هیچ کلید محرمانه در جای نامطمئن نباشد؛
     - هزینه صفر باشد؛
     - CI بیش از چند دقیقه طولانی‌تر نشود.
   - اگر معیارها برآورده نشد، همان کار با TypeScript ساخته می‌شود و یک ADR می‌ماند که می‌گوید «امتحان شد، نه، و چرا».
