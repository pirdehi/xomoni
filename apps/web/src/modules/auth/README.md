# `modules/auth`: identity and sessions

Everything about who someone is on xomoni.com: creating an account with a confirmed email address, signing in with a password or Google, two-step verification with an authenticator app, recovering a forgotten password, changing email or password, signing out and deleting the account. Other modules and routes get the signed-in person only through `server/session.ts` (`currentViewer`, `requireViewer`, `requireAccount`, `requireSecondFactorStep`). Decisions: [ADR-0011](../../../../../docs/adr/0011-email-and-password-sign-in.md), [ADR-0036](../../../../../docs/adr/0036-two-step-verification-with-an-authenticator-app.md).

## Flows

| Flow                | Route(s)                                                         | What happens                                                                                                                                                                                                                                                                                                                      |
| ------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sign up             | `/signup` → email → `/auth/confirm`                              | Validate, create the account (captcha), email a confirmation link; the link signs the person in and opens `/dashboard`. Same answer if the address already has an account. `?next=` (same-site) rides in the account's metadata, so the confirmation link returns to it, such as `/connect` or `/welcome` (#244); *Already have an account? Sign in* keeps it too.                               |
| Resend confirmation | `/signup` (after submit), `/login`                               | Offered after sign-up and when sign-in says the email isn't confirmed.                                                                                                                                                                                                                                                            |
| Sign in             | `/login`                                                         | Email and password (captcha), or Google. `?next=` returns to the page that asked, same-site only; *New to Xomoni? Create an account* keeps it (#244).                                                                                                                                                                                                                                 |
| Forgot password     | `/forgot-password` → email → `/auth/confirm` → `/reset-password` | The link signs the person in for recovery; an account with an authenticator app gives a code first (`/login/two-factor`); they choose a new password and land on `/account`.                                                                                                                                                                                                                                     |
| Change password     | `/account`                                                       | Needs the current password (checked by signing in again) and the captcha; with an authenticator app, a code from it too, since signing in again starts an `aal1` session. Google-only accounts set one through an emailed link instead.                                                                                                                                                                                           |
| Change email        | `/account` → two emails → `/auth/confirm`                        | Both the old and the new address must confirm; the page shows the pending change.                                                                                                                                                                                                                                                 |
| Google              | `/login`, `/signup` → Google → `/auth/callback`                  | PKCE flow started in the browser; the callback trades the code for a session.                                                                                                                                                                                                                                                     |
| Sign out            | `POST /auth/signout`                                             | Ends the session on this device; with `?scope=everywhere` (_Sign out everywhere_ on `/account`) every session of the account, so other browsers can no longer renew theirs (#83). Follows a same-site `?next=`. POST only, so a link can't sign anyone out, and only from the site's own pages: another `Origin` gets 403 (#147). |
| Delete account      | `/account`                                                       | Server Action; removes the user, devices and jobs, then signs out. The database refuses unless the person signed in within the last 10 minutes; the page then offers _Sign in again_, which signs out and returns to `/account` after sign-in (#80).                                                                              |
| Turn on two-step verification | `/account` | An optional name, then a QR code and its key, shown only now, then the app's first code (#173). Cancelling removes the unconfirmed app; one left from an earlier visit is removed before the next starts. A second app needs a code in this session (`aal2`). Supabase emails the account. |
| Sign in with a code | `/login` or Google → `/login/two-factor` → `?next=` | An account with an authenticator app goes to the code page after its password or Google, and on to the page that asked. Each of the account's apps is tried with the code. The page also says how to get back in without the app, and signs out. |
| Remove an app | `/account` | After a confirmation, from a session that gave a code (`aal2`): this page and Supabase both refuse below it. Removing the last app turns two-step verification off. Supabase emails the account. |
| Lost every app | email to privacy@xomoni.com | Not a page: the maintainer checks the address and a fresh sign-in, waits 3 days with the address told, then removes the apps ([SECURITY.md](../../../../../SECURITY.md#lost-authenticator-app)). |

## Security rules

- Sessions are verified on the server with `getClaims()` (signature-checked JWT), never `getSession()`; `authDeps()` calls `connection()` so session checks never run during a prerender.
- Two-step verification is checked on the server (#173, [ADR-0036](../../../../../docs/adr/0036-two-step-verification-with-an-authenticator-app.md)). `getSessionState` reads the `aal` claim from the verified token and, only below `aal2`, asks Supabase Auth whether the account has a verified app. A session that owes a code is not signed in: the proxy and `requireViewer`/`requireAccount` send it to `/login/two-factor`, `currentViewer` returns `null`, and the delete action refuses. The database's restrictive policies and account functions require the same (`public.mfa_satisfied()`).
- Interactive auth runs in the browser so Supabase's per-IP limits and Turnstile apply to the person ([ADR-0011](../../../../../docs/adr/0011-email-and-password-sign-in.md)).
- No account enumeration: sign-up, reset and resend give the same answer for unknown addresses; sign-in uses one message for "wrong password" and "no such account".
- Emailed links are checked by `parseEmailLink` (type allow-list, token format) and verified only on click, so link scanners can't use them up.
- Every `next` passes through `safeNextPath`.
- People see `AUTH_ERROR_MESSAGES`; provider errors go to logs only.
- The password policy here and in `supabase/config.toml` must match; `credentials.test.ts` fails if they drift.

## Tests

- Unit (`npm test -w @xomoni/web`): domain rules and every use case against an in-memory gateway, including the failure and enumeration cases.
- End to end (`npm run test:e2e -w @xomoni/web`, needs `supabase start`): every flow above in Chromium against local Supabase Auth, reading the real emails from Mailpit. Two-step verification's user scenarios ([`docs/scenarios/173-two-step-verification.md`](../../../../../docs/scenarios/173-two-step-verification.md)) are `e2e/two-factor.spec.ts`, each test named by its id and tagged `@task-173`. Signing up and in from /welcome and back, the links between the two pages included, are among /welcome's ([`docs/scenarios/244-welcome.md`](../../../../../docs/scenarios/244-welcome.md), `e2e/welcome.spec.ts`, tagged `@task-244`).
