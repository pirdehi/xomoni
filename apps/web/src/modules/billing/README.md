# `modules/billing`: payments with Polar

Paid plans on xomoni.com ([ADR-0042](../../../../../docs/adr/0042-payments-and-entitlements-with-polar.md)). Polar is the merchant of record: people pay on Polar's checkout, and the cloud keeps only each account's plan (`entitlements`, written only by Polar's signed webhook through `apply_billing_event`, [`supabase/`](../../../../../supabase/README.md)). Nothing here starts, resumes or approves anything on X (ADR-0006), and no X content goes to Polar (ADR-0004).

The webhook (#421) is here, with reading a person's plan for the pages. Checkout and the customer portal come next in #421, `/pricing` and `/account/billing` in #422.

## Layers

| Layer | Files | Responsibility |
| --- | --- | --- |
| `domain/` | `polar-event.ts`, `plan.ts` | `parsePolarEvent(body, catalog)`: Polar's webhook body (`unknown`, ADR-0016) as one change to a plan, an event to skip, or not an event. Strict: an object with a `type` and a `data` object; for the subscription events (`subscription.created`, `.updated`, `.active`, `.canceled`, `.uncanceled`, `.revoked`, `.past_due`, `.cycled`, `.paused`, `.resumed`) and the pass's order events (`order.paid`, `order.refunded`), exactly the fields it reads in Polar's types, else invalid. The account is the customer's `external_id`, a Supabase user id; the plan comes from the product, by the ids in the server's configuration (`Catalog`). Polar's statuses map onto ours: `trialing` and `active` as they are; `past_due` and `unpaid` keep the period; a cancel at the period's end is `canceled` until then; `revoked`, an ended subscription, `paused` and `trial_ended` close now; `incomplete` is skipped. A pass lasts 30 days from its purchase and a refund ends it. The change is dated by Polar's `modified_at`, else `created_at`, and marked `founding` when bought with the founders' discount. Skipped: other types, no Xomoni account, another product, unpaid, and a subscription's own orders. The person's email and name, which Polar's payload carries, are never read. `plan.ts`: `PlanView`, the plan a page shows (`signed_out`, `known`, or `unavailable`, never Free when it couldn't be read), and `hasPaidPlan`. |
| `application/` | `apply-webhook.ts`, `read-entitlement.ts` | `applyWebhook(ports, headers, body)`: 413 over 512 KB; 401 for a bad or stale signature, before anything is read; 400 for a body that isn't one of Polar's events; 202 for one no plan depends on; 500 when the database fails, so Polar retries; else 200 with the store's result (`applied`, `stale`, or `ignored` for a repeat). `readEntitlement(ports)`: no plan for a visitor; `unavailable` when the read fails. |
| `infrastructure/` | `webhook-signature.ts`, `supabase-admin.ts`, `supabase-billing.ts` | `verifyWebhook(headers, body, secret, now)`: the Standard Webhooks signature Polar puts on each delivery (`webhook-id`, `webhook-timestamp`, `webhook-signature`), an HMAC-SHA256 of `<id>.<timestamp>.<raw body>` keyed with the secret's UTF-8 bytes, as Polar's own SDK keys it. Web Crypto's `verify` compares it in constant time, and only within 5 minutes of its timestamp, either way; any one of several `v1,` signatures may match, so Polar can rotate its secret. `adminBillingStore()`: the only holder of Supabase's service-role key (`SUPABASE_SERVICE_ROLE_KEY`), `server-only`, no session; it calls `apply_billing_event` and nothing else, and passes no database message on. Null without the key. `readMyEntitlement(supabase)`: `my_entitlement()` with the person's own session, read strictly with `@xomoni/entitlements`; anything else is no reading. |
| `server/` | `webhook-route.ts`, `config.ts`, `plan.ts` | `handleBillingWebhook(request)`, the body of `POST /api/billing/webhook`: 503 until Polar's secret and the service-role key are set, 413 for a declared body over the limit, then `applyWebhook`. It answers `{ "result": … }` and logs one line per delivery (the outcome, the status, the webhook id and the type), never the body, an email or a key. `config.ts`: Xomoni's products (`POLAR_PRODUCT_PLUS_MONTHLY`, `…_PLUS_YEARLY`, `…_PRO_MONTHLY`, `…_PRO_YEARLY`, `…_PLUS_PASS`), the founders' discount (`POLAR_FOUNDING_DISCOUNT_ID`) and the webhook's secret, from the server's environment; missing ones never break the build. `currentPlan()`: the signed-in person's `PlanView`, for the pages. |

The route is `app/api/billing/webhook/route.ts`, thin.

## Rules

- **Only a signed webhook writes a plan.** The route checks the signature before it reads the body, and writes only through `apply_billing_event`, with the `service_role` key, from one `server-only` module that only the route may import (`web-service-role-is-webhook-only`). CI fails if a server key's name or value is in the browser bundle (`tooling/check-browser-bundle.mjs`).
- **No test reaches the real Polar.** Unit tests use `test/fakes/polar.ts` (a fake API, failures on demand, and `signTestEvent`, an independent signer with Node's own HMAC); the browser tests use `e2e/support/polar.ts` (a fake Polar on localhost, which the website's server finds at `POLAR_API_URL`). `test/setup.ts` and `e2e/support/test.ts` fail any test that asks polar.sh for anything.
- **Polar's keys are environment variables** (`apps/web/.env.example`), never in code, a pull request or a log.

## Tests

- `domain/polar-event.test.ts`: every subscription status and event, the pass and its refund, the founders' discount, the dates, and each skip and refusal; nothing about the person in a change.
- `application/apply-webhook.test.ts`: each answer (200, 202, 400, 401 before reading, 413 before checking, 500); `read-entitlement.test.ts`: signed out, known, unavailable.
- `infrastructure/webhook-signature.test.ts`: an event the fake Polar signed passes; another secret, a changed body, a signature moved to another id or time, a time more than 5 minutes away, a missing or malformed header, and a signature of another version or shape don't; any one of several signatures may match; an empty secret is the server's error.
- `infrastructure/supabase-admin.test.ts`: no key, no store; only `apply_billing_event`, with no session; no database message passed on. `supabase-billing.test.ts`: the reading and each refusal.
- `server/webhook-route.test.ts`: the route with the real signature check and an in-memory `apply_billing_event`: once only, an older event changes nothing, a forged body, another secret and no signature are refused, 503 until configured, and the log keeps no body, email, key or id of the person.
- The fake's own tests are in `test/fakes/polar.test.ts`. `e2e/polar.spec.ts` proves the fake Polar in a browser. `e2e/billing-webhook.spec.ts` posts signed events to the running site against the local Supabase: a purchase reaches `entitlements` once, and a forged body, another secret and no signature write nothing.
